ELFパーサーが完成したので、ここからはリンカー本体の実装に入っていく。
ただ、いきなり実装に飛び込むと迷子になりやすいので、本章ではリンク処理の全体フローと、最終的にどんな出力ができ上がるのかを先に整理しておく。

## リンク処理の全体フロー

リンカーは大まかに次の順番で処理を進めていく。

1. ELFヘッダーの解析（セクションヘッダーの位置などを取得）
2. セクションヘッダーの取得（各セクションの位置、サイズ、属性を取得）
3. 各種セクションの取得（シンボルテーブル、再配置情報など）
4. シンボル解決（未定義シンボルと定義済みシンボルを紐付け）
5. セクションの結合と配置（`.text`と`.data`を結合し、メモリアドレスを決定）
6. 再配置の適用（シンボル参照先アドレスを実際のアドレスに書き換え）
7. ELF出力（ELFヘッダー、セクション、セクションヘッダーをファイルに書き出し）

1〜3はすでに前章までで実装済みのELFパーサーが担当する部分である。
本章以降は、4以降の処理を順番に実装していくことになる。

## リンク処理の全体像

最終的なコードはざっくり次のようなイメージになる。

```rust
pub fn link_to_file(&mut self, inputs: Vec<Vec<u8>>) -> Result<Vec<u8>> {
    // 1. 入力ファイルをパース
    for (idx, input) in inputs.iter().enumerate() {
        let obj = Elf::parse(input).map_err(|e| LinkerError::Parse(format!("{:?}", e)))?;
        self.add_object(format!("input_{}", idx), obj);
    }

    // 2. シンボル解決
    let mut resolved_symbols = self.resolve_symbols()?;

    // 3. セクション配置
    let (output_sections, section_name_offsets) =
        self.layout_sections(&mut resolved_symbols)?;

    // 4. 実行ファイルの書き出し
    let mut out = std::io::Cursor::new(Vec::new());
    self.write_executable(
        &mut out,
        resolved_symbols,
        output_sections,
        section_name_offsets,
    )?;

    Ok(out.into_inner())
}
```

入力ファイルをパースして、シンボル解決して、セクションを配置して、書き出す。

## メモリレイアウト

実行ファイルのメモリレイアウトは次のようになる。

```
アドレス空間
┌─────────────────┬──────────────┐
│ 0x000000        │ Reserved     │
├─────────────────┼──────────────┤
│ 0x400000        │ ELF Header   │  ベースアドレス
├─────────────────┼──────────────┤
│ 0x400040        │ Program      │
│                 │ Header       │
├─────────────────┼──────────────┤
│ 0x400100        │ .text        │  コードセクション
│                 │ (executable) │
├─────────────────┼──────────────┤
│ 0x410110        │ .data        │  データセクション
│                 │ (read/write) │  0x10000のギャップ
└─────────────────┴──────────────┘
```

ベースアドレス`0x400000`は、GNU `ld`がAArch64 Linux向けにデフォルトで使う値なので、本書の自作リンカーもそれに倣っている。

`.text`と`.data`の間に`0x10000`（64KB）のギャップを空けているのには理由がある。以降で順に説明する。

### メモリ保護とページ

OSはメモリの保護属性をページ単位で管理している。
ページサイズはアーキテクチャとカーネル設定によって変わる。

- x86_64: 4KB
- AArch64: 4KB、16KB、64KB（カーネル設定による）

そして各ページには「読み取り可能」「書き込み可能」「実行可能」という属性を設定できる。
今回扱うセクションだと、それぞれに必要な属性は次のようになる。

- `.text`: 読み取り可能 + 実行可能（RX）
- `.data`: 読み取り可能 + 書き込み可能（RW）

これは前章で見たセクションフラグから決まる属性で、`.text`は`SHF_ALLOC | SHF_EXECINSTR`（`readelf`の表示で`AX`）、`.data`は`SHF_ALLOC | SHF_WRITE`（`WA`）が立っている。詳しくはSystem V ABI（[gABI](https://refspecs.linuxfoundation.org/elf/gabi4+/ch4.sheader.html#special_sections)）の特別セクション一覧に規定されている。

### ページ境界で分離する理由

もし`.text`と`.data`が同じページに乗ってしまうと、そのページにはRWXの全部が必要になる。
だがRWX（読み書き実行可能）なメモリはセキュリティ上危ない。攻撃者が書き込み可能な領域に悪意のあるコードを注入し、それを実行できてしまうからである。

ページ境界でちゃんと分離しておけば、`.text`のページはRX、`.data`のページはRWと、必要最小限の権限だけを与えられる。

### なぜ64KBか

実行中のカーネルのページサイズ自体は`getconf PAGESIZE`などで確認できる。ただし、リンカーが生成する実行ファイルは別環境にコピーされて実行される可能性もあるため、リンク時のホストのページサイズに合わせて決め打ちすると、そこでしか安全に動かないバイナリになってしまう。

ページサイズごとに必要なギャップは次のとおりである。

- 4KBページ設定のカーネル → 4KBのギャップで十分
- 64KBページ設定のカーネル → 64KBのギャップが必要

もし4KBしかギャップを空けていないと、64KBページ設定のカーネル上では`.text`と`.data`が同じページに入ってしまう可能性がある。

64KB（`0x10000`）のギャップを空けておけば、AArch64でサポートされるすべてのページサイズ（4KB、16KB、64KB）で確実に別々のページに乗る。実行環境を問わず安全側に倒すため、ここでは64KBを採用している。

## シンボル解決の概要

シンボル解決でやることは次のとおり。

1. すべてのオブジェクトファイルからシンボルを集める
2. 同名シンボルの解決（未定義 → 定義済み、バインディングの強さで判断）
3. 重複定義のエラーチェック
4. 未解決シンボルのエラーチェック

たとえば`main.o`の未定義シンボル`x`は、`sub.o`の定義済みシンボル`x`と紐付ける、というのが具体例である。

## セクション配置の概要

セクション配置でやることは次のとおり。

1. 各オブジェクトファイルの`.text`セクションを結合
2. 各オブジェクトファイルの`.data`セクションを結合
3. 結合後のセクションにメモリアドレスを割り当てる
4. シンボルのアドレスを更新する

## 再配置の概要

再配置でやることは次のとおり。

1. 各再配置エントリを処理
2. 参照先シンボルのアドレスを取得
3. 命令のアドレスと参照先アドレスから相対アドレスを計算
4. 命令の即値フィールドを書き換え

次章からは、これらを1つずつ実装していく。
