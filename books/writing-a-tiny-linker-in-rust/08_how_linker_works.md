本章では、リンク処理の全体フローを解説する。
実装に入る前に、リンカーが何をしているのかを説明する。

## リンク処理の全体フロー

リンカーは次の処理を順番に行う。

1. **ELFヘッダーの解析** - ファイル内のセクションヘッダーの読み取り開始位置などを取得
2. **セクションヘッダー情報の取得** - 各セクションの位置、サイズ、属性を取得
3. **各種セクション情報の取得** - シンボルテーブル、再配置情報などを取得
4. **シンボル解決** - 未定義シンボルと定義済みシンボルを紐付け
5. **セクションの結合と配置** - `.text`と`.data`を結合し、メモリアドレスを決定
6. **再配置の適用** - シンボル参照先アドレスを実際のアドレスに書き換え
7. **ELF出力** - ELFヘッダー、セクション、セクションヘッダーをファイルに書き出し

## リンク処理の全体像

コードで表現すると次のようになる。

```rust
pub fn link_to_file(&mut self, inputs: Vec<Vec<u8>>) -> Result<Vec<u8>, Error> {
    // 1. 入力ファイルをパース
    for input in inputs {
        let obj = parser::parse_elf(&input)?.1;
        self.objects.push(obj);
    }

    // 2. シンボル解決
    let mut resolved_symbols = self.resolve_symbols()?;

    // 3. セクション配置
    let (output_sections, section_name_offsets) =
        self.layout_sections(&mut resolved_symbols)?;

    // 4. 実行可能ファイルの書き出し
    let mut out = std::io::Cursor::new(Vec::new());
    self.write_executable(
        &mut out,
        resolved_symbols,
        output_sections,
        section_name_offsets,
    )?;

    Ok(out.into_inner())
}
```

## メモリレイアウト

実行可能ファイルのメモリレイアウトは次のようになる。

```
アドレス空間
┌─────────────────┬──────────────┐
│ 0x000000        │ Reserved     │
├─────────────────┼──────────────┤
│ 0x400000        │ ELF Header   │  ベースアドレス
├─────────────────┼──────────────┤
│ 0x400040        │ Program      │
│                 │ Header       │
├─────────────────┼──────────────┤
│ 0x400100        │ .text        │  コードセクション
│                 │ (executable) │
├─────────────────┼──────────────┤
│ 0x410110        │ .data        │  データセクション
│                 │ (read/write) │  0x10000のギャップ
└─────────────────┴──────────────┘
```

ベースアドレスは`0x400000`で、これはLinuxの標準的な実行可能ファイルのベースアドレスである。

`.text`と`.data`の間には`0x10000`（64KB）のギャップを設けている。この理由を説明する。

### メモリ保護とページ

OSはメモリ保護をページ単位で管理する。ページサイズはアーキテクチャとカーネル設定に依存する。

- x86_64: 4KB
- AArch64: 4KB、16KB、64KB（カーネル設定による）
  - 参考: [Memory Layout on AArch64 Linux](https://www.kernel.org/doc/html/latest/arch/arm64/memory.html)

各ページには保護属性（読み取り可能、書き込み可能、実行可能）を設定できる。

- `.text`: 読み取り可能 + 実行可能（RX）
- `.data`: 読み取り可能 + 書き込み可能（RW）

### ページ境界で分離する理由

もし`.text`と`.data`が同じページ内に存在すると、そのページには両方の属性が必要になる（RWX）。
しかし、RWX（読み書き実行可能）メモリはセキュリティ上危険である。攻撃者が書き込み可能な領域に悪意のあるコードを注入し、それを実行できてしまうためである。

ページ境界で分離することで、`.text`のページはRX、`.data`のページはRWと、必要最小限の権限だけを付与できる。

### なぜ64KBか

カーネルがどのページサイズで設定されているかは、実行時までわからない。

- 4KBページ設定のカーネル → 4KBのギャップで十分
- 64KBページ設定のカーネル → 64KBのギャップが必要

もし4KBのギャップしか設けていない場合、64KBページ設定のカーネルでは`.text`と`.data`が同じページに入ってしまう可能性がある。

64KB（`0x10000`）のギャップを設けることで、AArch64でサポートされるすべてのページサイズ（4KB、16KB、64KB）で確実に異なるページに配置される。

## シンボル解決の概要

シンボル解決では、次の処理を行う。

1. すべてのオブジェクトファイルからシンボルを収集
2. 同名シンボルの解決（未定義→定義済み、バインディングの強さで判断）
3. 重複定義のエラーチェック
4. 未解決シンボルのエラーチェック

例えば、`main.o`の未定義シンボル`x`は、`sub.o`の定義済みシンボル`x`と紐付けられる。

## セクション配置の概要

セクション配置では、次の処理を行う。

1. 各オブジェクトファイルの`.text`セクションを結合
2. 各オブジェクトファイルの`.data`セクションを結合
3. 結合後のセクションにメモリアドレスを割り当て
4. シンボルのアドレスを更新

## 再配置の概要

再配置では、次の処理を行う。

1. 各再配置エントリを処理
2. 参照先シンボルのアドレスを取得
3. 命令のアドレスと参照先アドレスから相対アドレスを計算
4. 命令の即値フィールドを書き換え
