本章では、リンカーの歴史や種類について学び、実際にリンクを行ってリンカーが何をしているのかを説明する。

## リンカーの歴史

リンカーはコンピュータの黎明期から存在するツールである。なぜリンカーが必要になったのか、その背景を説明する。

### 分割コンパイルの必要性

初期のコンピュータはメモリ容量が非常に限られていた。大きなプログラムを一度にコンパイルすることは困難であり、プログラムを複数のファイルに分割してコンパイルする必要があった。

分割コンパイルには次のようなメリットがある。

- **メモリ効率**: 大きなプログラムでも部分ごとにコンパイルできる
- **コンパイル時間の短縮**: 変更したファイルだけを再コンパイルすればよい
- **チーム開発**: 複数人で別々のファイルを同時に開発できる

### プログラムの部品化

分割コンパイルが可能になると、よく使う機能を「ライブラリ」として部品化し、複数のプログラムで再利用できるようになった。

例えば、数学関数（`sin`、`cos`など）やファイル操作関数（`fopen`、`fread`など）は、多くのプログラムで共通して使用される。これらを毎回書くのではなく、ライブラリとして提供し、必要なプログラムにリンクする方式が確立された。

リンカーは、このような分割コンパイルされたオブジェクトファイルやライブラリを結合し、実行可能ファイルを生成する役割を担っている。

## リンク方式の種類

リンクには大きく分けて2種類の方式がある。

### 静的リンク

静的リンクは、コンパイル時にすべてのオブジェクトファイルとライブラリを結合して、単一の実行可能ファイルを生成する方式である。

```
main.o + sub.o + libmath.a → a.out（単一の実行ファイル）
```

ライブラリを含めるため、実行ファイルのサイズが大きくなるが

- 依存ライブラリが不要
- 実行時のオーバーヘッドがない

というメリットがある。

### 動的リンク

動的リンクは、実行時に共有ライブラリ（`.so`ファイル）を結合する方式である。
コンパイル時のリンカーは共有ライブラリへの参照情報を実行ファイルに埋め込み、実行時に動的リンカー/ローダー（`ld.so`など）が実際のライブラリを読み込んでシンボルを解決する。

```
main.o + sub.o → a.out
                   ↓ 実行時（動的リンカー/ローダーが処理）
              libc.so（共有ライブラリ）
```

静的リンクと比べ、ライブラリを含めないため実行ファイルのサイズが小さいが、実行時にリンク処理が発生するためオーバーヘッドがある。
また、ビルド時と実行時で共有ライブラリのバージョンが異なると、シンボルが見つからない、ABIの非互換などの理由で実行できないことがある。このような環境差分の問題は動的リンク特有の課題である。

### 本書で実装するリンカー

本書では**静的リンクのみをサポートするリンカー**を実装する。
動的リンクをサポートするにはPLT（Procedure Linkage Table）やGOT（Global Offset Table）など、追加の仕組みが必要となり複雑になるためである。

静的リンクでも、リンカーの本質的な処理であるシンボル解決、セクション配置、再配置を学ぶことができる。

## 環境構築

本書ではDocker Composeを使って開発環境を構築する。
ARM64 Linux向けのリンカーを実装するため、Linuxコンテナ内で開発を行う。

まず、プロジェクトのルートディレクトリに`compose.yaml`を作成する。

```yaml:compose.yaml
services:
  linker-develop:
    image: rust:1.92-slim-bullseye
    container_name: linker-develop
    volumes:
      - .:/work
      - cargo-cache:/root/.cargo
    working_dir: /work
    tty: true
    entrypoint: /bin/bash

volumes:
  cargo-cache:
    name: linker-develop-cargo-cache
```

次のコマンドでコンテナを起動し、シェルに入る。

```sh
$ docker compose up -d
$ docker compose exec linker-develop bash
```

## サンプルプログラムの作成

本書で作成する最もシンプルなELFは、変数を終了ステータスコードとして使用するプログラムである。

まず、2つのソースファイルを作成する。

```c:main.c
__asm__(
      ".global _start\n"
      "_start:\n"
      "    adr     x0, x\n"
      "    ldr     w0, [x0]\n"
      "    mov     x8, #93\n"
      "    svc     #0\n"
);
```

```c:sub.c
int x = 11;
```

`main.c`はインラインアセンブリで`_start`エントリポイントを定義している。このアセンブリは、変数`x`の値を読み取り、その値を終了ステータスとしてプログラムを終了する処理を行う。

`sub.c`は変数`x`を値`11`で初期化している。

## オブジェクトファイルの生成

GCCを使ってオブジェクトファイルを生成する。

```sh
$ gcc -c main.c -o main.o
$ gcc -c sub.c -o sub.o
```

`-c`オプションはコンパイルのみを行い、リンクは行わないことを指定する。

## ldを使ったリンク

標準のリンカー`ld`を使ってリンクを行い、動作を確認する。

```sh
$ ld -o a.out main.o sub.o
$ ./a.out
$ echo $?
11
```

終了ステータスが`11`となり、正しくリンクされていることが確認できた。

## リンカーが行う処理

リンカーは`main.o`と`sub.o`を入力として受け取り、実行可能ファイル`a.out`を出力した。この過程でリンカーが行った処理を説明する。

なお、ELFファイルの中身を確認するには`readelf`コマンドを使う。オプションによってヘッダー、セクション、シンボルなど様々な情報を表示できる。

### シンボル解決

シンボルとは、プログラム内の関数名や変数名などの識別子のことである。オブジェクトファイル内では、これらのシンボルはシンボルテーブルに登録され、リンカーがシンボルを通じて各オブジェクトファイル間の参照関係を解決する。

`main.o`は変数`x`を参照しているが、`x`の定義は持っていない。`readelf -s`でシンボルテーブルを確認すると、`x`が未定義（`UND`）として登録されていることがわかる。

```sh
$ readelf -s main.o | grep -E "Ndx| x$"
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     9: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND x
```

一方、`sub.o`には`x`が定義されている。

```sh
$ readelf -s sub.o | grep -E "Ndx| x$"
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     8: 0000000000000000     4 OBJECT  GLOBAL DEFAULT    2 x
```

リンカーは`main.o`の未定義シンボル`x`と`sub.o`の定義済みシンボル`x`を紐付ける。これがシンボル解決である。

### セクション配置

オブジェクトファイルには`.text`（コード）や`.data`（データ）などのセクションがある。リンカーはこれらのセクションを結合し、実行時のメモリアドレスを決定する。

リンク後の`a.out`のセクションを確認すると、アドレスが割り当てられていることがわかる。

```sh
$ readelf -S a.out | grep -E "Nr|\.text|\.data"
  [Nr] Name              Type             Address           Offset
  [ 1] .text             PROGBITS         00000000004000e8  000000e8
  [ 2] .data             PROGBITS         00000000004100f8  000000f8
```

### 再配置

`main.o`の`adr x0, x`命令は、変数`x`のアドレスを参照している。しかし、コンパイル時点では`x`の最終的なアドレスは不明である。

リンカーはセクション配置後に`x`のアドレスが確定したら、この命令を書き換えて正しいアドレスを埋め込む。これが再配置である。

`main.o`の再配置情報を確認する。

```sh
$ readelf -r main.o
Relocation section '.rela.text' at offset 0x180 contains 1 entry:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
000000000000  000900000112 R_AARCH64_ADR_PRE 0000000000000000 x + 0
```

出力の詳細は次章で説明するが、ここでは「`.text`セクションの先頭（`Offset`が0）にある命令が、シンボル`x`を参照しており、リンク時に書き換えが必要」という情報が記録されていることを押さえておけばよい。

### 実行可能ファイルの生成

最終的に、リンカーはELFヘッダー、プログラムヘッダー、各セクションを適切に配置した実行可能ファイルを出力する。

```sh
$ readelf -h a.out | grep Type
  Type:                              EXEC (Executable file)
```

`Type`が`EXEC`となり、OSが実行できる形式になっている。

## まとめ

本章で学んだリンカーの処理の流れを図にまとめる。

```
┌─────────────────────────────────────────────────────────────────┐
│   main.o              sub.o                                     │
│   ├─ .text           ├─ .data                                   │
│   └─ adr x0, x       └─ x = 11                                  │
└─────────────────────────────────────────────────────────────────┘
                              ↓
1. シンボル解決
┌─────────────────────────────────────────────────────────────────┐
│    main.o undefined x  ←→  sub.o defined x                      │
└─────────────────────────────────────────────────────────────────┘
                              ↓
2. セクション配置
┌─────────────────────────────────────────────────────────────────┐
│    .text → 0x4000e8                                             │
│    .data → 0x4100f8  （x のアドレスが確定）                         │
└─────────────────────────────────────────────────────────────────┘
                              ↓
3. 再配置
┌─────────────────────────────────────────────────────────────────┐
│    adr x0, x  →  adr x0, 0x4100f8                               │
│    （x の参照を実際のアドレスに書き換え）                             │
└─────────────────────────────────────────────────────────────────┘
                              ↓
4. 出力
┌─────────────────────────────────────────────────────────────────┐
│   a.out (Executable)                                            │
│   ├─ ELF Header                                                 │
│   ├─ Program Header                                             │
│   ├─ .text (0x4000e8)                                           │
│   └─ .data (0x4100f8)                                           │
└─────────────────────────────────────────────────────────────────┘
```
