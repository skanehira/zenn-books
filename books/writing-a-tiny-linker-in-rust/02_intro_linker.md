本章では、リンカーの簡単な歴史や種類、実際にリンク時に何をしているのかをざっくり説明していく。

## リンカーの歴史

初期のコンピュータはメモリ容量が非常に限られていた。
そのため大きなプログラムを一度にコンパイルすることは難しく、プログラムを複数のファイルに分割してコンパイルする必要があった。

分割コンパイルにすると、次のようなメリットがある。

- メモリ効率がよい：大きなプログラムでも部分ごとにコンパイルできる
- コンパイル時間が短い：変更したファイルだけ再コンパイルすればよい
- チーム開発がしやすい：複数人で別々のファイルを同時に開発できる

そして分割コンパイルが普通になってくると、よく使う機能を「ライブラリ」として部品化し、複数のプログラムで使い回そうという発想が出てくる。
たとえば`sin`、`cos`のような数学関数や`fopen`、`fread`のようなファイル操作関数は、いろいろなプログラムで共通して使うものだ。これらを毎回書くのは無駄なので、ライブラリとして提供して必要なプログラムにリンクする、というやり方が確立された。

リンカーはこのような分割コンパイルされたオブジェクトファイルやライブラリを結合し、実行ファイルに仕上げる役割を担っている。

## リンク方式の種類

リンクの方式は大きく分けて2種類ある。図1のように、静的リンクは実行ファイルに必要なライブラリをすべて含めるのに対し、動的リンクは実行時にライブラリを読み込む。

![](/images/writing-a-tiny-linker-in-rust/ch02-02-static-vs-dynamic-linking.png)
*図1*

### 静的リンク

静的リンクは、コンパイル時にすべてのオブジェクトファイルとライブラリを結合して、単一の実行ファイルを生成する方式である。
ライブラリも全部入りなので実行ファイルのサイズは大きくなるが、

- 依存ライブラリが不要
- 実行時のオーバーヘッドがない

というメリットがある。

### 動的リンク

動的リンクは、実行時に共有ライブラリ（`.so`ファイル）を結合する方式である。
コンパイル時のリンカーは共有ライブラリへの参照情報を実行ファイルに埋め込んでおき、実行時に動的リンカー/ローダー（`ld.so`など）が実際のライブラリを読み込んでシンボルを解決する。

静的リンクに比べてライブラリを含めない分ファイルサイズは小さくなるが、実行時にリンク処理が走るのでオーバーヘッドがある。
また、ビルド時と実行時で共有ライブラリのバージョンが違うと、シンボルが見つからない、ABIの非互換などで実行できないことがある。

このあたりの面倒くささがあるので、筆者は基本的に静的リンクを好んで使っている。

### 本書で実装するリンカー

本書では**静的リンクのみをサポートするリンカー**を実装する。
動的リンクをサポートしようとするとPLT（Procedure Linkage Table）やGOT（Global Offset Table）といった仕組みが必要になり、複雑になるからである。
最小限の静的リンクを実装することで、リンカーの本質的な処理であるシンボル解決、セクション配置、再配置はしっかり学べる。

## 環境構築

本書ではDocker Composeを使って開発環境を構築する。
ARM64 Linux向けのリンカーを実装するので、Linuxコンテナの中で開発するのが一番楽である。

まずプロジェクトのルートディレクトリに`compose.yaml`を作成する。

```yaml:compose.yaml
services:
  linker-develop:
    image: rust:1.95-slim-bullseye
    container_name: linker-develop
    volumes:
      - .:/work
      - cargo-cache:/root/.cargo
    working_dir: /work
    tty: true
    entrypoint: /bin/bash

volumes:
  cargo-cache:
    name: linker-develop-cargo-cache
```

次のコマンドでコンテナを起動し、シェルに入る。

```sh
$ docker compose up -d
$ docker compose exec linker-develop bash
```

以降のコマンドはこのコンテナ内で実行する前提で進める。

## サンプルプログラムの作成

本書で扱う一番シンプルなELFは、変数を終了ステータスとして使うだけのプログラムである。

まず2つのソースファイルを作成する。

```c:main.c
__asm__(
      ".global _start\n"
      "_start:\n"
      "    adr     x0, x\n"
      "    ldr     w0, [x0]\n"
      "    mov     x8, #93\n"
      "    svc     #0\n"
);
```

```c:sub.c
int x = 11;
```

`main.c`はインラインアセンブリで`_start`エントリポイントを定義していて、変数`x`の値を読み取ってそれを終了ステータスとしてプログラムを終了する。
`sub.c`は変数`x`を`11`で初期化しているだけのファイルである。

次に`gcc`を使ってオブジェクトファイルを生成する。
`-c`オプションはコンパイルだけ行い、リンクはしないという指定である。

```sh
$ gcc -c main.c -o main.o
$ gcc -c sub.c -o sub.o
```

最後に、標準のリンカー`ld`を使ってリンクし、実行してみる。

```sh
$ ld -o a.out main.o sub.o
$ ./a.out
$ echo $?
11
```

終了ステータスが`11`になり、ちゃんとリンクされていることが確認できる。

## リンカーが行う処理

`ld`は`main.o`と`sub.o`を入力として受け取り、実行ファイル`a.out`を出力したとき、
内部で何をやっているのかをここでざっくり説明していく。

なお、ELFファイルの中身を覗くには`readelf`コマンドが便利で、オプションによってヘッダーやセクション、シンボルなどを表示できる。

### シンボル解決

シンボルとは、プログラム内の関数名や変数名のような識別子のことである。
オブジェクトファイル内では、これらのシンボルはシンボルテーブルに登録され、リンカーはシンボルを介して各オブジェクトファイル間の参照関係を解決する。

`main.o`は変数`x`を参照しているが、`x`そのものの定義は持っていない。
`readelf -s`でシンボルテーブルを確認すると、`x`が未定義（`UND`）として登録されているのがわかる。

```sh
$ readelf -s main.o | grep -E "Ndx| x$"
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     9: 0000000000000000     0 NOTYPE  GLOBAL DEFAULT  UND x
```

一方、`sub.o`には`x`が定義されている。

```sh
$ readelf -s sub.o | grep -E "Ndx| x$"
   Num:    Value          Size Type    Bind   Vis      Ndx Name
     8: 0000000000000000     4 OBJECT  GLOBAL DEFAULT    2 x
```

リンカーはこの`main.o`の未定義シンボル`x`と`sub.o`の定義済みシンボル`x`を紐付ける。これがシンボル解決である。

### セクション配置

オブジェクトファイルには`.text`（コード）や`.data`（データ）といったセクションがある。
リンカーはこれらを結合して、実行時にどのアドレスに配置するかを決める。

リンク後の`a.out`のセクションを見ると、ちゃんとアドレスが割り当てられている。

```sh
$ readelf -S a.out | grep -E "Nr|\.text|\.data"
  [Nr] Name              Type             Address           Offset
  [ 1] .text             PROGBITS         00000000004000e8  000000e8
  [ 2] .data             PROGBITS         00000000004100f8  000000f8
```

### 再配置（リロケーション）

`main.o`の`adr x0, x`命令は、変数`x`のアドレスを参照している。
ただし、コンパイル時点では`x`が最終的にどのアドレスに置かれるかはわからない。

そこでリンカーはセクション配置で`x`のアドレスが確定したあと、この命令を書き換えて正しいアドレスを埋め込む。これが再配置である。

`main.o`の再配置情報は次のように確認できる。

```sh
$ readelf -r main.o
Relocation section '.rela.text' at offset 0x180 contains 1 entry:
  Offset          Info           Type           Sym. Value    Sym. Name + Addend
000000000000  000900000112 R_AARCH64_ADR_PRE 0000000000000000 x + 0
```

ここでは「`.text`セクションの先頭（`Offset`が0）にある命令が、シンボル`x`を参照していて、リンク時に書き換えが必要」という情報が記録されている。
出力の詳しい意味は次章で説明する。

### 実行ファイルの生成

最後に、リンカーはELFヘッダー、プログラムヘッダー、各セクションを適切に並べた実行ファイルを出力する。

```sh
$ readelf -h a.out | grep Type
  Type:                              EXEC (Executable file)
```

`Type`が`EXEC`になっており、OSが実行できる形式になっている。
